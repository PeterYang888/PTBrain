# 史丹佛 AI 系統課程深度解析：從大型語言模型到 Agentic Workflow

這份簡報文件旨在深入探討史丹佛大學「BLLM」課程的核心內容，解析 AI 工程師如何透過「重軸（Augmenting LLM）」技術，將基礎語言模型轉化為具備商業價值的實戰系統。

---

## 執行摘要 (Executive Summary)

目前的 AI 發展可分為橫軸（提升基礎模型能力）與重軸（工程技術疊加）。對大多數開發者與企業而言，真正的價值在於**重軸（Augmenting LLM）**的應用。透過提示詞工程（Prompt Engineering）、檢索增強生成（RAG）以及 Agentic Workflow，開發者能克服基礎模型（Base Model）缺乏專業知識、資訊落後、難以控制以及長文本理解力退步等四大限制。本文詳細分析了如何從單一模型的能力強化，進階到具備複雜決策能力的「智能體工作流（Agentic Workflow）」，並強調「評估體系（Evaluation）」在產品上線過程中的決定性作用。

---

## 關鍵主題詳細分析

### 1. 強化單一模型的技術路徑
在開發 AI 產品時，僅靠更換更強的基礎模型（如從 GPT-4 升級到 GPT-5）通常不足以解決商業場景中的具體問題。開發者需掌握以下三種工具：

*   **提示詞工程 (Prompt Engineering)：** 這是工程師的基本功。研究顯示使用者分為「半人馬（Centaur，分工委派型）」與「生化人（Cyborg，高頻協作型）」模式。最重要的技術是**提示詞鏈（Prompt Chaining）**，將複雜任務拆解為多個獨立 Prompt，前一個的輸出作為後一個的輸入，以提升可觀察性與測試效率。
*   **微調 (Fine-tuning)：** 史丹佛教授建議「能不做就不做」。其缺點包括需要大量優質數據、容易過度擬合（Overfit）、實效性差且遷移成本高。僅在法律、科學等需要極高重複精度，或基礎模型表現極其吃力的特定領域才建議使用。
*   **檢索增強生成 (RAG)：** 解決模型幻覺與資訊落後的標準方案。透過向量資料庫（Vector Database）儲存語義向量，並利用**分塊（Chunking）**與多層次存儲技術，在模型推理時提供精確的外部參考文件。即使未來模型上下文窗口（Context Window）變長，RAG 在降低延遲與及時更新資例方面仍具優勢。

### 2. 從單一模型到系統設計 (Agentic Workflow)
「智能體工作流」是指將提示詞、外部工具與各項元件組合成有結構的系統。

#### 傳統軟體與 Agentic AI 軟體的對比
| 維度 | 傳統軟體 (Traditional) | Agentic AI 軟體 |
| :--- | :--- | :--- |
| **資料類型** | 結構化資料 (JSON, DB) | 自由文本、圖片、音訊 |
| **邏輯特性** | 確定性 (Deterministic) | 模糊性 (Fuzzy) |
| **架構思維** | 精確控制執行路徑 (Microservices) | 目標管理 (Manager Mindset) |
| **測試方式** | 可重複、確定性測試 | 迭代、探索式測試 |

#### 智能體 (Agent) 的三核心要素
1.  **提示詞 (Prompt)：** 定義角色與權限範圍。
2.  **上下文管理 (Context Management)：** 區分短期記憶（Working Memory）與長期記憶（Archival Memory），在有限窗口內保留關鍵資訊。
3.  **工具 (Tools)：** 賦予 Agent 執行能力（如搜尋、預訂、支付）與查詢能力（如訪問 CRM 或資料庫）。

### 3. 評估體系 (Evaluation/Evals)
評估是 AI 系統能否進入生產環境（Production）的命脈。教學中提出了三個維度的評估框架：

*   **整體 vs 組件：** 看最終回覆的滿意度，也看每一步拆解動作的精準度。
*   **客觀 vs 主觀：** 客觀指標（如訂單 ID 是否正確）可由腳本驗證；主觀指標（如語氣是否有同理心）需人工評分或使用 **LLM-as-judge**。
*   **定量 vs 定性：** 統計成功率與延遲，並深入分析幻覺發生的原因。

### 4. 多智能體協作 (Multi-agent Systems)
多智能體系統適用於需要「平行處理」或「跨團隊復用」的複雜場景。其溝通模式分為：
*   **科層制 (Hierarchical)：** 由一個統籌者（Orchestrator）派工，結構清晰。
*   **扁平制 (Flat)：** 智能體之間直接互通。
*   **MCP (Model Context Protocol)：** 作為通用協議層，讓 Agent 不需認識每個 API，簡化智能體間的通信。

## 重要語錄與背景解析

> **「Prompt Engineering 不會是一個職業，因為它是每個工程師都該會的基本技能，就像九九乘法表一樣。」**
*   **背景：** 針對市場上對「提示詞工程師」職位的熱議，史丹佛教授強調技術人員應將其視為必備的基礎功，而非單一專業。

> **「Agentic 系統的思維是 Think like a manager：你給 AI 一個目標和限制，讓它自己決定怎麼完成。」**
*   **背景：** 解釋傳統軟體工程師在轉向 AI 開發時，最大的挑戰在於從「精確控制每一行代碼」轉變為「管理邊界與方向」。

> **「Fuzzy 的問題一定要加上 Human-in-the-loop。」**
*   **背景：** 在處理如考試評分等高風險場景時，AI 雖然能進行模糊判斷（Fuzzy Scoring），但必然會犯錯，因此必須設計申訴機制，由真人介入審查。

## 具體實踐指引 (Actionable Insights)

### 1. 任務拆解 (Task Decomposition) 第一優先
在打造 AI Agent 前，應先觀察真人如何處理該任務。將大任務拆解成細碎的小步驟（如：抽資訊、查資料庫、對比政策、起草、發信），並決定哪些步驟使用確定性代碼（Deterministic），哪些使用 LLM。

### 2. 採用「硬編碼工具 (Hardcoded Tools)」起步
對於 Agent 的自主性，建議從第二層級開始：給予一組固定的工具，讓 Agent 自行決定執行的步驟與順序。這在可控性與靈活性之間達到了最佳平衡。

### 3. 建立自動化評估流程
不要只依賴人工隨機抽查。實作步驟如下：
*   **錯誤分析 (Error Analysis)：** 人工標註少量負面案例。
*   **設計 Rubric：** 將問題轉譯為具體的評分標準（如：1分代表贅字多，5分代表精簡）。
*   **AB 測試：** 在固定底層模型的情況下測試 Prompt 變體，或在固定 Prompt 的情況下測試不同模型的表現。

### 4. 避免過度工程 (Over-engineering)
在引入 Multi-agent 或 Fine-tuning 之前，先問自己：單一 Agent 或簡單的 Prompt Chaining 是否已經能解決問題？工程設計應保持簡單，僅在需要平行處理或提升特定領域精度時才增加複雜度。
