## 一句話摘要
本影片深入解析如何透過撰寫、層級分類與動態「修剪」**`CLAUDE.md`**（或 Codex 的 **`agent.md`**），以最優化 AI 的**指令預算（Instruction Budget）**與 Token 消耗，打造高效率的 AI 協作開發工作流 [1, 2]。

## 主講者背景
*   **主講者/頻道名稱**：**Gary Chen** [1]。
*   **講述風格與立場**：風格實用且具深度，立場偏向實戰派 AI 開發。他強調 AI 的能力與程式碼庫都是動態流動的（Becoming），開發者應抱持與 AI 協同進化的心態，定期優化指令檔案 [3, 4]。

## 核心論點
*   **`CLAUDE.md` 的最高指導原則地位**：在 Claude Code 或 Codex 啟動對話時，系統會自動讀取並將 `CLAUDE.md` 的內容注入 Context Window，作為 AI 工作的最高指導原則，能大幅省去重複解釋專案架構的時間 [1, 5]。
*   **多層級（Hierarchical）規則設計**：規則可劃分為 **User-level**（個人長期偏好，置於使用者目錄的 `.code` 資料夾內）、**Project-level**（專案共同標準，置於專案根目錄）以及 **Nested-level**（子資料夾專屬規則，如前端 React 或後端 Python 獨立設定），各層級規則會依序疊加套用 [5, 6]。
*   **避免過度擬合「專案現狀」**：使用 `/init` 指令雖然能自動生成規格範本，但若塞入過多 AI 在背景啟動的 **`explorer subagent`** 本就能自行掃描獲得的客觀資訊，反而會浪費 Token 並佔用 Instruction Budget [2, 7, 8]。
*   **指令預算（Instruction Budget）的限制**：AI 在單次任務中能同時顧及的規則數量有限，過多冗餘指令會迫使 AI 分配注意力去判斷衝突與優先順序，導致真正重要的核心規則被淹沒 [2]。
*   **以減法與加法精鍊規則**：修剪原則在於「AI 翻看程式碼也猜不出的隱性知識」才夠格寫入；並可透過 5 個具體問題（如絕對禁忌、聯動關係、定義完成等）提取腦中經驗 [9, 10]。
*   **合適的資訊分流（Skills & Hooks）**：長且特定任務才需的流程應寫進 **`skill`** 中；而絕對不能犯的死罪（如上傳 API Key）則應透過 **`hook`**（在 Git commit 前強制檢查）來攔截，而非單靠 Markdown 提醒 [8]。
*   **花園式的「動態維護」**：利用 `/insights` 分析歷史對話產出 HTML 報告，自動生成推薦規則；並隨著模型升級（如 Fable 5 刪除 80% 系統提示規則）主動修剪不再需要的過期限制 [11, 12]。

## 關鍵細節與數據
*   **CLI 指令**：
    *   **`/init`**（影片中音譯為 `sinit` 或 `slashinit`）：用於在專案資料夾中快速掃描並生成第一版 `CLAUDE.md` 的初始模板 [7]。
    *   **`/insights`**（影片中音譯為 `ins` 或 `sinites`）：在 Claude Code 內輸入，可分析歷史對話記錄並產生一份 HTML 報告，提供規則、Skill 或 Hook 的優化建議 [11]。
*   **檔案路徑與檔名**：
    *   **`CLAUDE.md`**（Claude Code 使用的專案設定檔）[1]。
    *   **`agent.md`**（Codex 中與 `CLAUDE.md` 相對應的設定檔）[1]。
    *   **`CLAUDE.local.md`**（僅留在本機電腦、不隨 Git 上傳的個人工作偏好檔）[6]。
    *   **`.code`**（User-level 檔案所在的資料夾，置於使者目錄之下）[5]。
    *   **`package.json`**（AI 在背景會自動掃描的專案檔，無須手動寫入 `CLAUDE.md`）[2]。
*   **設定與結構範例**：
    *   **User-level 偏好範例**：主講者在個人層級定義了「只能用中文繁體輸出」、「用第一性原理思考」與「用金字塔原理結構化輸出」 [5]。
    *   **Nested-level 隔離範例**：專案下同時包含 `frontend`（React / 專屬 UI 規範）與 `backend`（Python / 獨立邏輯）資料夾，可分別放置獨立的 `CLAUDE.md` 以免規則混淆 [6]。
    *   **Single Source of Truth 同步法**：在 `CLAUDE.md` 的第一行直接 reference `agent.md`，即可同時維護兩邊，讓 AI 透過 reference link 讀取單一源頭 [13]。
*   **關鍵數據**：
    *   **80%**：官方團隊在為 Fable 5 與 Opus 5 優化系統提示時，一口氣刪除了超過 **80%** 的規則，而能力完全沒有退步，證實模型變聰明後舊規則反而會變成限制 [12]。

## 重要引言
*   「**我真心覺得把這個檔案寫好絕對是你用 AI 投資報酬率最高的一件事。**」—— 談論撰寫 `CLAUDE.md`（或 `agent.md`）對開發效率的關鍵影響 [1]。
*   「**規則放得越接近實際工作的檔案，適用範圍就越精確。**」—— 說明 Nest-level 設計與規則疊加的運作邏輯 [7]。
*   「**其實一份好的 CLAUDE.md 就像一個花園，它的維護工作只有兩件事：新增與修剪。**」—— 闡述動態維護規則檔案的哲學 [11]。 * 「**世界上海沒有任何東西是有重點的，一切都在變成下一個版本的過程之中。**」—— 引用凱文·凱利《必然》中的 "Becoming" 概念，說明代碼庫、AI 能力與 `CLAUDE.md` 都是流動且需要不斷進化的 [3, 4]。

## 與其他工具或做法的關聯
*   **Codex (及 `agent.md`)**：與 Claude Code 對應的工具。在 Codex 中，功能相同的對應檔案稱為 `agent.md`（或稱為 agency markdown），兩者背後的優化邏輯完全通用 [1]。
*   **Git / GitHub**：Project-level 的 `CLAUDE.md` 通常會跟隨程式碼一起上傳至 Git，確保團隊協作時每個人都遵循相同的 AI 指示限制；而 `CLAUDE.local.md` 則不傳上雲端，僅保留在個人本機 [5, 6]。
*   **Git Hooks (Pre-commit hook)**：對於絕對不能犯的死罪（例如將 API key commit 上去），不應只寫在 `CLAUDE.md` 中，而應該使用 Hook（在 commit 前用程式強制檢查並直接擋下），避免 AI 在任務複雜時漏掉指示 [8]。
*   **Explorer Subagent**：Claude Code 在執行任務時，背景自動啟動的子代理。它會自行掃描專案目錄、`package.json` 等檔案，因此無需在 `CLAUDE.md` 中贅述這些客觀現狀 [2, 7]。
*   **官方 Prompting Guides**：如 Anthropic 發布 Fable 5 或 Codex 發布 5.6 的官方指南，是進行 `CLAUDE.md` 規則修剪與更新時最客觀的參考依據 [12]。
*   **Patreon 資源**：Gary 將整套「修剪與檢查 CLAUDE.md」的體檢 Prompt 放到 Patreon 上，幫助用戶定期整理檔案並與新模型（如 Opus 5）對齊 [3, 13]。
